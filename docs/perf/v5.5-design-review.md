# v5.5 设计评审：基于 v5.4 实测数据的瓶颈分析

> 结论先行：设计稿里 4 个新增能力里，**2 个是有效的（Pipeline 解锁、Metrics）**，**2 个打错了目标（Adaptive Chunk、Checkpoint Batch）**，而 **500MB/s 这个目标在当前架构下不可能达到**——不是优化不够，是目标和瓶颈不匹配。

## 一、先看数据说了什么

`bottleneck-matrix.sh` 的饱和曲线（16MiB payload，100 workloads）：

| 并发 | 吞吐 (MB/s) | 延迟 p50 | target_queue_wait p50 |
|---|---|---|---|
| 1 | 68.4 | 241ms | 0ms |
| 2 | 106.0 | 311ms | 11ms |
| 4 | 120.8 | 551ms | 93ms |
| **8** | **126.7** ← 峰值 | 1060ms | 341ms |
| 16 | 122.1 | 2209ms | 983ms |
| 32 | 122.3 | 4307ms | 1985ms |
| 64 | 122.3 | 8787ms | 4107ms |
| 100 | 116.0 | 13893ms | 6965ms |

三个事实：

1. **吞吐在并发 8 触顶**，之后加并发不再增长（100 并发时反而下降 8%）。
2. **延迟随并发线性爆炸**：8→100 并发，延迟涨 13 倍。
3. **加速比只有 1.85x**（1→8 并发），远低于 8x。

第 3 条是决定性的。Amdahl 定律说，加速比 1.85x 意味着**串行部分占了约 46%**。加 worker 不会解决它——worker 再多，串行段还是串行。

## 二、锁到底占了多少

从 c8 的 `target_metric_delta` 反推（600 个 batch 请求）：

| 指标 | 累计 | 每 batch |
|---|---|---|
| fsync | 4438ms | 7.4ms |
| state_save | 3803ms | 6.3ms |
| write | 234ms | 0.4ms |
| **锁内小计** | **8475ms** | **14.1ms** |
| queue_wait | 33168ms | 55.3ms |

对照墙钟 13239ms：

```
锁内工作时间  8475ms  = 墙钟的 64%
锁外(controller 往返 + HTTP)  4764ms = 墙钟的 36%
```

**这就是关键**：拆掉 `s.mu` 最多让 Target 侧吞吐提升到 100/64 = **1.56x**，从 126.7 MB/s 到约 198 MB/s。

**剩下 36% 在锁外**，那是 controller 驱动的 `prepare → transfer → activate → commit` 串行往返，以及每 migration 的 PostgreSQL 事务。设计稿只盯着那 64%，注定拿不到 4-5x。

## 三、为什么锁内那 64% 也拆不快

我实测了本机磁盘（`dd` 写 512MiB）：**4.4 GB/s**，而且 `/tmp` 在 macOS 上是内存文件系统。

也就是说 `fsync` 的 7.4ms **不是磁盘物理上限**，是别的东西：

- Target 每次 batch `fsync` 时把**同一文件**的多个 chunk 合并刷盘；并发下不同 migration 写不同文件，但都在同一个 page cache 压力下
- `state_save` 6.3ms 是**写状态 JSON 文件 + fsync**，每个 batch 一次，这是纯粹的小文件同步开销
- 这两项都是**同步阻塞**操作，把它们放进 worker pool 并不会变快，只会让更多 goroutine 一起堵在磁盘队列上

**换句话说**：把 8 个 worker 的 pipeline 套在这个锁外面，等于 8 个 goroutine 争抢一个依然串行的 fsync 流水线。吞吐不会翻倍，延迟会更难预测。

## 四、逐条评审设计稿的 4 个新增能力

### 4.1 Pipeline Transfer Engine —— 方向对，实现危险

**方向对**：`target.go:245` 那把 `s.mu` 确实把不同 migration 的 batch 完全串行化了，`queue_wait` 占墙钟 250%（多 goroutine 同时等同一把锁）就是铁证。解锁是唯一能提升吞吐的正确方向。

**但设计稿的实现有三处硬伤**：

```go
// ① queue 无缓冲，workers 拿不到真正的 pipeline 效果
queue := make(chan Chunk)

// ② 生产者在主 goroutine，ctx 传进来却没用
//    ctx 取消后这里会永久阻塞在 queue<-c
for _, c := range chunks {
    queue <- c
}

// ③ transferChunk 忽略错误 —— 任何写失败都被吞掉，
//    但上层会当作成功继续走到 activate/commit
transferChunk(c)
cp.Record(c)
```

第 ③ 条最危险：这个代码库的核心不变式是**可恢复 + 幂等**，吞掉 transfer 错误会直接破坏它。

**还有设计稿没提到的问题**：`s.states[id]` 是 `TargetServer` 上的共享 map，`st.Files[c.Path]` 的 `f.Chunks[c.Index] = c.SHA256` 是**去重状态**。拆锁后两个 batch 同时改同一个 `f.Chunks` map 会 data race，幂等去重逻辑会崩。这不是加个 `sync.Map` 能解决的——`f` 本身是指针，多个 goroutine 拿到的是同一个 `*FileState`。

### 4.2 Adaptive Chunk —— 打错了目标

设计稿让 chunk 从 4MB 涨到 64MB。但看实测：

```
batch_count_p50 = 6   (所有并发档位都是 6)
transfer_batch_bytes = 4194304  (4MiB，未变)
```

**batch 数从头到尾没变过**。因为 v5.4 已经在做 4MiB 批传输了，`TRANSFER_BATCH_BYTES` 才是控制 round-trip 的旋钮，而 `chunk_size` 只是在 batch 内部切分。

把 chunk 调大**不会减少 batch 数**，所以不会减少 fsync 和 state_save 的次数——而那正是 64% 墙钟的来源。

真正该调的是 `TRANSFER_BATCH_BYTES`（4MiB → 8/16MiB），代码里上限是 16MiB（`MaxBatchBytes`）。这**不需要新代码**，一个环境变量就能测。

### 4.3 Checkpoint Batch —— 打错了目标

设计稿想每 16 个 chunk 才持久化一次。但 `state_save` 的成本是 **per-batch** 的，而 checkpoint 是 per-chunk 累积的。把 16 个 chunk 合成一次持久化，减少的是 chunk 级的状态写入次数——而实测里根本没有 chunk 级状态写入（状态是 batch 完成后整份写的，见 `target.go:358-366` 的 `if stored > 0`）。

**更严重的是：这会直接破坏崩溃恢复语义。** 当前是每 batch 落盘 state，崩溃时最多丢一个 batch（幂等重发即可）。改成 16 个 chunk 才落盘，崩溃时最多丢 16 个 batch 的进度——`chaos.sh` 的 CASE 1/2 会直接挂。

**这是拿正确性换性能，而换的还不是瓶颈。**

### 4.4 Metrics —— 有效，但已经存在

设计稿要新增 `/metrics` 端点和 5 个指标。实际上 v5.4 **已经**有：

```
migration_transfer_bytes_total
migration_transfer_chunks_total
migration_target_batch_queue_wait_ms_total
migration_target_batch_peak_inflight
migration_transfer_bytes_total
```

这次 benchmark 的 `controller_metric_delta` / `source_metric_delta` / `target_metric_delta` 就是从它们算出来的。

缺的只有 `migration_active_workers` 这类 gauge，以及"常驻"形式而非累计值的形式。这是小事，不是 v5.5 的主战场。

## 五、500MB/s 这个目标

**在当前架构下不可能达到**，除非改变架构假设。

数学上：单 Target 进程，锁内 14.1ms/batch，每 batch 4MiB：

```
硬上限 = 4MiB / 14.1ms = 297 MB/s   （假设锁内 100% 塞满，无任何 controller 往返）
```

实测 126.7 MB/s 是这个数的 43%，差额就是那 36% 的锁外时间。

要达到 500MB/s，只有三条路：

| 路径 | 代价 | 性质 |
|---|---|---|
| A. 多 Target 进程 + 负载均衡 | Target 本身要能多实例，state 得共享（现在在内存 map 里） | 架构变更，state 得外置 |
| B. 去掉 fsync / 改用 group commit | 崩溃恢复语义改变，违背"可恢复"核心不变式 | ❌ 否决 |
| C. 增大 `TRANSFER_BATCH_BYTES` 到 16MiB | 零代码，只改环境变量 | **先做这个** |

路径 C 是零成本的，先花 10 分钟验证——**在动任何代码之前**。

## 六、我建议的顺序

不要一次性做 v5.5。按证据优先级：

### 第 0 步：零代码，先测 ✅ 已执行，见下文

### 第 1 步：修锁的粒度（不是拆锁，是分片）

`TargetServer.mu` 保护了三件不相干的事：

1. `s.states[id]` map（state 查找）
2. `st.Files[c.Path]` 的 chunk 去重（幂等性）
3. 文件写 + fsync（磁盘 IO）

正确做法是**按 migration 分片锁**（`[N]sync.Mutex`，N=16/32，按 `id` 哈希取模）：

- 不同 migration 完全并行 → 拿到并发收益
- 同一 migration 仍串行 → **幂等语义不变，chaos 测试不破**
- 不需要动 `f.Chunks` 的数据结构 → 无 data race

**这是最小的正确改法**，一行锁变一个分片数组。

### 第 2 步：解掉那 36% 的锁外时间

这是真正的天花板所在，也是设计稿完全没提的部分。查 `target_batch_http_p50=473ms` 里有多少是 controller 的同步往返——大概率是 controller 在 `prepare`/`activate`/`commit` 阶段串行等 DB。

对应 5 个阶段在 c8 的耗时：

| 阶段 | p50 |
|---|---|
| create | 7ms |
| prepare | 158ms |
| transfer | 682ms |
| activate | 95ms |
| commit | 94ms |
| **合计** | **1036ms** |

transfer 外的 `prepare+activate+commit = 347ms`，占 33%。这才是要动的地方。

### 第 3 步：才考虑 pipeline

如果第 1、2 步做完，锁内外的分布会完全改变。**那时候再看需不需要 pipeline，而且应该基于新的 profile 决定，而不是现在。**

## 七、总结

| 设计稿能力 | 判定 | 理由 |
|---|---|---|
| Pipeline Transfer Engine | ⚠️ 方向对，实现不可用 | 锁该拆，但吞错误 + data race 会破坏核心不变式；应先做分片锁 |
| Adaptive Chunk | ❌ 打错目标 | batch 数恒为 6，改 chunk 不减少 fsync；该调的是 `TRANSFER_BATCH_BYTES` |
| Checkpoint Batch | ❌ 破坏正确性 | 减的不是瓶颈次数，且让 chaos 崩溃恢复挂掉 |
| Metrics | ✅ 已存在 | 只需补 gauge 形式 |
| 500MB/s 目标 | ❌ 当前架构不可达 | 锁内硬上限 297MB/s；需先解架构 |

**最重要的一条**：设计稿把 `target_queue_wait` 当成需要消除的敌人，但**等锁时间不是浪费，是排队**。它高恰恰证明锁是瓶颈——而拆锁只能拿到 1.56x。另外 36% 在锁外，那才是设计稿没看到的天花板。

**建议先跑第 0 步**（改一个环境变量，10 分钟），用数据决定 v5.5 到底该做什么，而不是照着一份写着 500MB/s 的设计稿去实现。

## 附录：第 0 步实测结果（已完成）

固定 `concurrency=8`、`payload=16MiB`、`workloads=100`，**只改 `TRANSFER_BATCH_BYTES` 一个变量**：

| batch | 吞吐 (MB/s) | batch 数 | target 请求数 | fsync p50 | state_save p50 | queue p50 | 延迟 p50 |
|---|---|---|---|---|---|---|---|
| 4MiB（当前默认） | 115.0 | 6 | 554 | 39.0ms | 37.0ms | 293.0ms | 990.1ms |
| **8MiB** | **150.1** | 4 | 400 | 32.0ms | 25.5ms | 214.5ms | 895.9ms |
| 变化 | **+30.5%** | −33% | −28% | −18% | −31% | −27% | **−9.5%** |

**结论：假设成立。** batch 数减少 1/3，吞吐涨 30.5%，而且**延迟还降了 9.5%** —— 没有牺牲任何东西。

这直接证实了两件事：

1. **fsync 密度确实是主因**（batch 6→4，每 batch 锁内成本 76ms→57.5ms，吞吐随之上涨）
2. **设计稿的 Adaptive Chunk 是改错了旋钮** —— 该动的是 `TRANSFER_BATCH_BYTES`，而且**连改都不用改代码**

### 顺带发现一个真实 bug

试 `TRANSFER_BATCH_BYTES=16MiB`（代码里的 `MaxBatchBytes` 上限）时 **100 个 workload 全部失败**：

```
BATCH_ENCODE_FAILED: encoded batch exceeds 16777216 bytes
```

原因：`MaxBatchBytes` 同时当作**配置上限**和**编码后体积上限**。当 batch 配置等于 16MiB 时，编码开销（每 chunk 的 header）把它顶过自身上限，于是**任何 payload 都无法配置 16MiB batch**。

这是个边界条件缺陷，不是配置错误 —— 用户按文档设 `TRANSFER_BATCH_BYTES=$((16*1024*1024))`（README 里明确写"允许 256KiB..16MiB"）必然踩到。**修法**：编码校验留出余量，或把「配置上限」与「硬上限」拆成两个常量。

## 修订后的建议

既然一个环境变量就换来 +30.5%，v5.5 的优先级应重排：

| 优先级 | 动作 | 预期收益 | 成本 |
|---|---|---|---|
| **1** | 默认 batch 4MiB → 8MiB（一行默认值，或直接改文档建议） | **+30%** 已实测 | 近乎零 |
| **2** | 修 16MiB 边界 bug | 消除必然踩到的失败 | 小 |
| 3 | `TargetServer.mu` 分片锁（按 migration id 哈希） | 解不同 migration 间的串行 | 中，不破幂等 |
| 4 | 降低 controller 往返占比（那 36%） | 未知，需先 profile | 中 |
| — | ~~Pipeline Engine~~ | 收益重叠，且实现有正确性风险 | 大 |
| — | ~~Adaptive Chunk~~ | 改错旋钮 | 中 |
| — | ~~Checkpoint Batch~~ | 破坏崩溃恢复 | 中 |
